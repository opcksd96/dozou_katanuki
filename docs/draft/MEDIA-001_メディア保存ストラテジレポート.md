本ドキュメントは、x_timeline_app における **ユーザーメディア（テキスト、画像、動画等）の動態的な保存ポリシー** を、MVVMアーキテクチャとデータベース仕様に基づいて整理したものです。メディア種別ごとの保存期間、更新頻度、バックアップ方法、暗号化要否、削除ルールを明記し、永続的な保存を実現するための包括的戦略を記載します。

## 詳細内容

### 1. メディア種別の分類と保存ポリシー

x_timeline_app では、取得対象とするSNS（Twitter/X等）から取得されるコンテンツを以下の3種類に分類し、それぞれ独立した保存ポリシーを適用します。

| 区分 | メディア種別 | データベーステーブル | ストレージ方式 | 保存期間 |
|------|--------------|---------------------|----------------|----------|
| A | テキスト（ツイート本文、コメント） | `tweets` | SQLite3（メインDB: chronoarchive.db） | 永久保存 |
| B | 静止画・アニメーションGIF | `media` | Stashapp + ローカルストレージ | 2年間保持 |
| C | 動画（MP4、WebM等） | `media` | Stashapp + 外部ストレージ | 6か月間保持 |

### 2. テキストメディア（ツイート本文）の保存戦略

#### 2.1 保存方式
- **データベース**: `chronoarchive.db` の `tweets` テーブルに保存
- **保存粒度**: ツイートID（tweet_id）を主キーに、編集履歴を version カラムで管理
- **更新頻度**: リアルタイムでの取得（ポーリング間隔：5分）

#### 2.2 保存形式
```sql
-- tweets テーブルの主要カラム
tweet_id: TEXT (PK)
account_id: TEXT (FK: accounts.id)
full_text: TEXT
created_at: DATETIME
updated_at: DATETIME
version: INTEGER (MVCC用バージョン番号)
wayback_url: TEXT (アーカイブ参照)
status: TEXT (active/deleted/archived)
```

#### 2.3 バックアップ方法
1. **日次フルバックアップ**: SQLiteの `VACUUM INTO` コマンドで差分バックアップを取得
2. **週次コールドバックアップ**: S3等の外部ストレージへのアップロード
3. **月次アーカイブ**: 変更ログベースの差分抽出と Wayback Machine の連携

#### 2.4 暗号化とセキュリティ
- **保存時**: データベース全体の暗号化は必要なし（個人情報の抽出が困難なため）
- **転送時**: HTTPSによるTLS暗号化を全ての外部通信に適用
- **アクセス制御**: アカウントIDに基づくRLS（Row Level Security）の実装を検討

### 3. 静止画メディアの保存戦略

#### 3.1 保存方式
- **プライマリストレージ**: Stashappを中心としたローカルファイルストレージ
- **フェッチ方法**: Twitter API の `media_url` から直接ダウンロード
- **ファイル名規則**: `{tweet_id}_{media_idx}_{YYYYMMDD}.{ext}`

#### 3.2 保存フロー
```
Twitter API → Media URL 取得 → Axiosダウンロード → 
ローカル一時保存 → Stash APIへアップロード → 
メタデータ登録（SQLite3 media テーブル）
```

#### 3.3 ライフサイクル管理
- **初期保存**: ダウンロード即Stashへアップロード
- **日次同期**: Mortix(ARIA2)経由でS3バックアップへの同期
- **削除トリガー**: 90日間アクセスログがない場合、Stashから論理削除
- **物理削除**: 180日後にファイルシステムから完全削除

#### 3.4 バックアップ方法
1. **ローカルRAID**: 2台のNVMe SSDでミラーリング
2. **クラウドバックアップ**: 月次でS3 Glacierへ移行
3. **検証方法**: SHA256ハッシュの一致による整合性確認

### 4. 動画メディアの保存戦略

#### 4.1 保存方式
- **プライマリストレージ**: Stashappの外部ストレージ連携機能を利用
- **ダウンロード**: JD2 DownloaderのAPIを呼び出して高速ダウンロード
- **トランスコード**: 再生効率のためにH.264 → H.265への圧縮変換

#### 4.2 品質管理基準
| 項目 | 基準値 |
|------|--------|
| 動画解像度 | 1080p以下（ストレージ節約） |
| コーデック | H.265（メイン）/ H.264（互換性） |
| ファイルサイズ上限 | 4.8GB（Stashの制限） |
| 圧縮率 | 元サイズの20〜30%目標 |

#### 4.3 ライフサイクル管理
- **アーカイブタイミング**: 30日後にWayback Machineへスナップショットを作成
- **削除期限**: 6か月間アクセスログがない場合、論理削除
- **保存期限**: 1年間保持（Waybackスナップショットは独立して永久保持）
- **代替取得**: Wayback Machineからの復元機能の実装

#### 4.4 帯域幅最適化
- **スロットリング**: ピークタイムのダウンロード速度制限（10MB/s）
- **並列処理**: 同時5ファイルまでの並列ダウンロード
- **再試行ロジック**: ネットワークエラー時に3回まで再試行

### 5. メディアの復元制御メカニズム

#### 5.1 復元フロー
```
[復元要求] 
    ↓
{認証・認可チェック}
    ↓
{Blob検索（キャッシュ + DB)}
    ↓ (存在確認)
{バージョン番号検証}
    ↓ (有効版)
{メディア復元ブロブ取得}
    ↓
{暗号解除 + 描画支援}
```

#### 5.2 キャッシュ戦略
- **キャッシュ対象**: 直近7日間にアクセスされたメディア
- **キャッシュ期間**: 15分（LRU eviction policy）
- **キャッシュ場所**: Redis（メイン） + ローカルディスク（バックアップ）

#### 5.3 整合性保証
- **ハッシュ検証**: 毎日3時にジョブ実行により `blobs` テーブルと実際のファイルを比較
- **監査ログ**: すべての復元・ダウンロード操作を `audit_log` テーブルに記録
- **改変検出**: HMAC（SHA3-384）による改竄検出

### 6. ストレージ最適化方策

#### 6.1 重複排除
- **指紋生成**: 各メディアファイルに対して SHA3-256 ハッシュを付与
- **重複判定**: 同じハッシュ値を持つファイルは1つのオブジェクトとして管理
- **期待削減効果**: 推定30-40%のストレージ容量削減

#### 6.2 階層ストレージ
```
ホットデータ（直近30日） → NVMe SSD
ウォームデータ（30日〜1年） → HDD
コールドデータ（1年以上） → AWS S3 Glacier Deep Archive
アーカイブデータ（Wayback統合） → Wayback Machine
```

#### 6.3 ライフサイクル自動化
- **バッチジョブ**: 毎日3時にJD2バッチを実行し、ライフサイクルルールを適用
- **自動移動**: アクセス頻度に基づいてストレージ階層を自動切替
- **容量アラート**: 使用量が85%を超えた場合、管理者に通知

### 7. 災害復旧計画（DRP）

#### 7.1 復元ポイント目標（RPO）
| データ種別 | RPO目標 |
|------------|----------|
| テキストデータ | 5分以内 |
| メディアメタデータ | 1時間以内 |
| メディアファイル | 24時間以内 |

#### 7.2 復元時間目標（RTO）
| データ種別 | RTO目標 |
|------------|----------|
| システム全体 | 4時間以内 |
| 個別メディア | 30分以内 |
| メタデータのみ | 15分以内 |

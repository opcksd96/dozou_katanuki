#### 2.1 SNSプラットフォームとデジタル消滅の危機
本システムがサルベージ対象とする主要プラットフォーム（Twitter/X, Instagram, TikTok等）は、中央集権的なWebサービスであるがゆえに、常にデータの恒久的喪失リスク（デジタル消滅）を孕んでいます [1, 6]。

##### 1. プラットフォーム固有の構造的破壊リスク
*   **アカウント凍結（BAN）とサイレントサスペンド**:  
    アカウントがサスペンドされた瞬間、CDN（Content Delivery Network）上のメディアアセット（アバター、画像、動画）へのリンクは瞬時に無効化（404 / 403）され、いいね履歴やリプライツリー情報が完全に消滅します [6]。
*   **短縮URL（t.co等）のリダイレクト破綻**:  
    プラットフォーム提供の短縮ドメインサーバーが停止または仕様変更した場合、投稿テキスト内に含まれるすべての外部リンク解決が不可能になり、一次情報のコンテキストが破壊されます [6]。
*   **メディアアセットの劣化・暗号化・ログインウォール**:  
    スクレイピングや直接閲覧を防ぐため、各SNSはタイムラインに対して強力なログインウォール（未ログイン時の閲覧制限）やCloudflareによるWAF（Web Application Firewall）保護を導入しており、通常手段での巡回・ローカル保存を厳しく排除しています [6, 72]。

##### 2. 「自動サルベージ」と「手動サバイバルルート」の2系統制御の必然性
この厳しい防御策を突破するため、本システムは以下の2系統のデータ回収ルートを採用し、100%の保全導通を保証します [66, 72]。
1.  **自動系統（Wayback CDX経由）**: 外部アーカイブが巡回・キャッシュした過去のHTML/JSONから自動でデータを吸い出すルート [66, 71]。
2.  **手動系統（手動取得WARCの逆引きインポート）**: ログイン済みの実ブラウザ（Webrecorder等）を介してユーザーが直接パケットを記録したWARCファイルを、完全オフラインで自動解析・展開するサバイバルルート [66, 72]。

#### 2.2 Wayback Machine (Internet Archive) と原本パケット保全技術
[Internet Archive Wayback Machine](https://archive.org/web/) は、本システムにおける最も強力な過去ログのデータリソース（タイムマシン）です [2, 78]。

##### 1. Wayback CDX Server API
Wayback Machineにキャッシュされている特定のURL、あるいはアカウント配下のスナップショット履歴を、高速かつ軽量にスキャンするためのクエリAPIです [7, 78]。
*   **エンドポイント規格**:  
    `https://web.archive.org/web/timemap/link/https://twitter.com/{username}`（Memento Timemap [7]）  
    `https://web.archive.org/cdx/search/cdx?url={platform_url}/*&output=json`（CDX API [7]）
*   **本システムでの活用法 (Scraper)**:  
    `scraper.py` は、CDX APIに対してアカウントのインデックスを高速走査し、過去にアーカイブされた投稿ID（PostID）とそれに対応するスナップショットの「タイムスタンプ（例: `20210510143000`）」のリストを $O(N)$ で一括抽出します [7, 65, 95]。

##### 2. Memento プロトコル (RFC 7089)
タイムスタンプに基づき、過去の特定の時点におけるリソース（HTTPヘッダーおよびボディ）を折衝・取得するための標準プロトコルです [7, 78]。
本システムは、RFC 7089 で定義された時間折協（Time Negotiation）の概念に準拠し、投稿された日時に最も近い（時刻誤差が最小の）メディアアセットやHTMLキャッシュを特定してピンポイント解決します [7, 59, 78]。

##### 3. warcio による一期一会の「オンザフライWARC」生成
Wayback Machineからフェッチするデータは、将来的にInternet Archive側のAPI閉鎖やサーバーエラーによって二度と手に入らなくなる可能性があります。  
そのため、自動サルベージ実行時、Pythonサイドカーは **`warcio`** ライブラリをHTTP通信（`requests`）に透過的に噛ませ、**「通信パケット（生のHTTPリクエスト、レスポンスヘッダー、およびバイナリペイロード）を1ビットも改ざん・歪曲することなく、そのまま 1つの圧縮コンテナ `snapshot.warc.gz` へストリーム保存する」**技術を適用します [65, 71, 97]。

```python
# scraper.pyにおけるオンザフライWARC保存のコアロジック (warcio)
import requests
from warcio.capture_http import capture_http

# 指定されたWaybackスナップショットURLからデータを取得しながら、
# 通信パケットを100%オリジナルの原本（ snapshot.warc.gz ）としてリアルタイムでダンプ
with capture_http('backups/dumps/twitter/msluo14/187938.../snapshot.warc.gz'):
    response = requests.get('https://web.archive.org/web/20260115.../https://twitter.com/...')
```
このWARCファイルはISO 28500に準拠した最高純度の原本証明であり、データベース（SQLite3）が万が一全損した場合でも、**完全オフラインで通信パケットをローカルにデコンプレス・リプレイするだけで全情報を再構築可能**にする、システムの「第2の心臓（Deep Path）」として機能します [72, 74, 96]。

#### 2.3 Aria2 ＆ Motrix による適応型メディアダウンロード技術
サルベージプロセスにおいて、投稿に添付された動画（MP4/M3U8）や高解像度静止画の実ファイルをローカルストレージ（Stash監視領域）に書き出す処理は、ネットワーク負荷とエラー耐性を最も要求されるレイヤーです [8, 55]。

##### 1. Motrix JSON-RPC 連携
[Motrix](https://motrix.app/) は、コマンドライン型マルチセッション・高速ダウンローダ **[Aria2](https://aria2.github.io/)** を内蔵した先進的なダウンロードマネージャーです [8, 9, 78]。
*   **RPCポート**: `:6800` (localhost)
*   **通信プロトコル**: WebSocket / HTTP JSON-RPC
*   **本システムでの活用 (Downloader)**:  
    `downloader.py` は、メディアの実ダウンロード処理を直接自プロセスのメモリ内で処理せず、Motrixに対して非同期のRPCコマンド `aria2.addUri` を発行してタスクを委譲します [9, 65]。これにより、マルチ接続（Multi-Connection）によるディスク帯域いっぱいの爆速並列ロード、および途中で中断されたダウンロードの自動レジューム（再開）機能を100%外部エンジンにオフロードします [8, 9]。

##### 2. downloader.py に義務付ける「3段階適応型フォールバック」ロジック
ローカル環境においてMotrixが未起動である場合、またはWayback Machineから一時的にアクセス拒否（HTTP 429/503等）を食らった場合でも、データ回収を中断させない堅牢な**適応型フォールバックアルゴリズム**を実装します。

1.  **RPC疎通チェック（第1優先）**:  
    `downloader.py` 起動時に `:6800`（Motrix JSON-RPC）への疎通確認を試みます。導通が確認できた場合、`aria2.addUri` 経由でマルチスレッド超高速ダウンロードを開始します [9]。
2.  **直接 HTTP 同期ストリーミング（第2優先フォールバック）**:  
    Motrixが起動していなかった場合（接続タイムアウト）、プロセスは即座に Python の `requests` ライブラリの同期直接ダウンロード（`stream=True` によるチャンク処理）へと自律的に切り替えます。
3.  **指数バックオフ付 429/503 エラーハンドリング**:  
    Wayback Machineなどの高負荷なアーカイブサーバーから、レートリミットを告げる `HTTP 429 Too Many Requests` や `HTTP 503 Service Unavailable` を受け取った場合、即時エラー終了を厳禁とします。  
    プロセスは以下の時間隔（秒）をあけて、**指数バックオフ（Exponential Backoff）**を伴う最大3回のリトライを自律的に実施します：
    $$\text{WaitTime} = 2^{\text{attempt}} \times \text{BaseInterval (例: 1.5秒)} + \text{jitter}$$
    リトライがすべて失敗した場合は、Wayback元URL（`original`）をSQLite3に書き込み、フロント側でいつでも再フェッチ要求が出せる状態（フォールバック表示）にします。

##### 3. メディア実体のハッシュ完全性検証 (Integrity Check)
ダウンロードが完了したメディアファイルは、Stashappにインジェクションする前に必ず**「破損チェック（Integrity Verification）」**を通過させなければなりません。
*   ファイルサイズが「0バイト」でないこと、および部分的な破損がないかを `os.path.getsize` でスキャン。
*   動画（Scene）や静止画（Image）の **OSHash** または **MD5ハッシュ** を算出し、ファイル名（BaseName）との同一性を整合します [8, 56]。

#### 2.4 Stash による作品ストリーミング ＆ ヘッドレスタスク統治
[Stashapp](https://stashapp.cc/) は、大容量の動画（H.264/H.265/VP9等）や静止画ライブラリを極めて高度に一元統治する、オープンソースの C++ 製メディアサーバーエンジンです [8, 78]。

##### 1. 本システムにおける Stashapp の役割
本システムにおいて、Stashapp（**:9999**）は、通常のUIをフロントエンドから完全に隠蔽した**「ヘッドレスな高速メディアデコーダ ＆ HLSストリーミングインジェクター」**として扱われます [64]。
*   **OSHash / Perceptual Hash による重複排除**:  
    同一の画像や同一の動画を、異なるアカウントや異なるタイミングで二重にインポートしても、Stashapp側でファイルコンテンツのハッシュ値を照合し、物理ディスク内での重複保存を完全に自動排除（De-duplication）します [8]。
*   **HLS（HTTP Live Streaming）自動トランスコーディング**:  
    本家SNSからサルベージした超大容量の動画（MP4/WebM）を、Stashappが裏で自動でマルチビットレートのHLSストリーム（m3u8および.tsセグメント）にトランスコードし、ネットワーク帯域に応じたサクサクとしたゼロディレイ再生環境を提供します [3, 8]。

##### 2. GraphQL API 経由の自動バインディング
Pythonサイドカー（Downloader）は、ハッシュ検証をクリアしたメディアファイルをStashの物理フォルダ（`stash/scenes/`、`stash/images/`）へ移動した後、Stashがローカルホスト閉塞ポート `:9999` でリッスンしている GraphQL API に対して以下のミューテーションを発行します [3, 8, 78]。
1.  アカウント名から Stash 内部の `Performer`（出演者）を検索または自動作成。
2.  「標準タイトル規約（`X (@msluo14): Tweet 187938...`）」に準拠したタイトルを付与して、動画（Scene）または静止画（Image）を登録 [61]。
3.  登録成功時にStashappから返却される一意のUUID（`stash_scene_id`、`stash_image_id`）を回収し、Core Backend (:5176) の `POST /api/posts` 経由で SQLite3 の `media` テーブルに書き戻します [43, 48, 61]。

##### 3. アバター隔離ポリシー（Avatar Isolation Policy）の技術的意義
アバターなどの小さく数が膨大なプロフィール画像は、Stashappが本来想定している「大容量ビデオコレクション」に紛れ込ませると、Stashの画像グリッド、サムネイル一覧、および出演者メタデータ領域を著しく汚染し、システムのパフォーマンス低下と画面崩壊（ノイズ混入）を招きます [60]。
そのため、**アバター画像実体はすべて `{middleware_root}/assets/{platform}/` に配置され、Stashの監視フォルダから物理的かつ完全に隔離されます（Avatar Isolation Policy）** [55, 60]。

#### 2.5 SQLite3 WALモード ＆ GORM メタデータデータ abstraction
メタデータ（投稿テキスト、アカウント情報、お気に入り状態、リレーション）の安全な不変保存と、ローカルミリ秒応答クエリを両立させるため、中核データベースに **SQLite3**（WALモード）および **GORM** オブジェクトリレーショナルマッピングを採用します [2, 9, 15]。

##### 1. SQLite3 WAL (Write-Ahead Logging) モード
通常のロールバックジャーナルとは異なり、読み込み処理と書き込み処理が一切衝突せずに並行して走る、ローカルデータベース最高水準の同時実行制御技術です [9, 78]。
*   **読み込みの一切の非ブロッキング**:  
    Pythonサイドカー（Mutator）がバックグラウンドで大量の投稿データを `POST /api/posts` 経由でデータベースに書き込んでいる最中であっても、フロントエンド（Vue 3）は一切のクエリラグ（遅延）なしに、タイムライン（`GET /api/posts`）をミリ秒応答で取得し、サクサクと無限スクロールできます [9, 30, 49]。
*   **ファイルの堅牢性**:  
    書き込み処理が中断されても、WALファイルによる整合性復旧が可能なため、データベース破損率を限りなく0%に抑え込みます [9]。

##### 2. GORM による不変構造抽象化 (Database Abstraction)
GORM（Go ORM）は、Goの型安全な構造体（GORM Models）をSQLite3のデータベーススキーマへと自動的にマッピング・マイグレーションします [15, 78]。
*   **インデックス ＆ リレーションシップの自動整合**:  
    開発者やAIエージェントが生SQLを自作して構文エラーを発生させる危険性を100%防止し、外部キー制約、インデックスチューニング、テーブル結合クエリをすべて Go コード側で型安全に統治・抽象化します [15, 29]。
